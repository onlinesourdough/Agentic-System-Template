# Establish a System contract

Use for an independently operable reusable capability. Resolve shared phase
procedures through AIOS as directed by local AGENTS; this route supplies the
System-specific ownership and adoption work.

1. Name purpose, operator, cohesive responsibilities, invoke condition, natural
   return and proof. If a method or bounded Project is sufficient, stop creation.
2. Inspect existing domain truth and prior operational evidence relevant to the
   change. Define only the durable state needed to continue operation; no
   universal layout, ledger, schema, database or runtime is required.
3. Establish repeatable domain operations, inputs/outputs, authority and stop
   boundaries, local criteria, failure evidence and recovery ownership. Use
   domain proof appropriate to the capability.
4. Turn the neutral identity into the concrete System's AGENTS and primary
   specialist skill. Add specialist methods or domain audit criteria only for
   actual recurring responsibilities. Give each maintained specialist SKILL.md
   its own quoted SemVer in YAML metadata.version, initially "1.0.0". Bump that
   skill independently: patch for compatible corrections, minor for compatible
   capabilities, major for breaking its invocation or operating contract. Keep
   skill versions distinct from System or package releases; do not create
   placeholder skills just to populate a shelf. Do not copy generic lifecycle, technology,
   repository audit or tracking procedures into the new System.
5. Complete the authorized contract and affected implementation, inspect the
   diff, and fix in-scope findings. Verify the concrete entrypoint, required
   dependencies, one natural outcome
   through its real interface, source provenance and recovery limitations.
   Return paths and current evidence to the invoking task; direct tasks need no
   additional worker or upstream lead.

The adopted System owns its criteria, skills, workspace and evolution. The seed
is no runtime dependency and never overwrites an existing System. Generic drift
review uses shared `aios-review-work`; a concrete domain audit may remain local.

Read only context that affects the responsibilities being established or changed.
Carry session authorization through implementation, checks and fixes; local
procedures do not require renewed approval for already authorized actions.
Pause only for a material missing decision, authority or required capability;
preserve independent acceptance and delivery boundaries when work is delegated.
For a narrow contract correction, inspect its affected instructions and links;
do not rerun operational journeys unless their behavior or proof changes.
